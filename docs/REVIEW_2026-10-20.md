## 保留の根拠

### F2・F3：録音を失う操作の対象が確定していない

`noteTransferFailure()`には失敗したコレクションの引数がありません。転送失敗イベントの発生位置にかかわらず`frontier.next`を失敗箇所と見なします。3回の通知が同一録音の独立した3回の試行だという保証もありません。

`noteOversized`について、合成データで次を再現しました。

```text
frontier.next = 100
noteOversized(start: 105, end: 106)
stallNeedingDecision != nil   // まだ100が未保存でも現在の停止として表示
skipStall()
frontier.next = 100           // スキップしても本来の停止は解消しない

noteOversized(start: 100, end: 101)
noteOversized(start: 110, end: 111)
stall.start = 110             // 本来の停止箇所を後続範囲が上書き
```

また、画面は確認ダイアログを表示したときの範囲を保存せず、承認時に最新の`service.stall`をスキップするため、確認後に別の録音を処理する可能性があります。スキップ保存後のネイティブ位置更新が失敗した場合も、「受信位置は変更していない」という表示が保存済みの状態と一致しません。

実装する場合は、失敗した録音全体の範囲と転送試行を型付きイベントで特定し、実際に先頭を塞ぐ範囲を保持してください。確認する対象を固定し、承認時にも同じ対象か照合する必要があります。周回境界・後続範囲の到着・永続化成功後のネイティブ更新失敗を含む試験も必要です。リング内データへの影響は、ライブラリの転送手順を確認してから説明します。

提案版のAutomaticQueueテストは、追加した`recording("g", ...)`が16進64桁のID制約を満たさず`invalidID`で停止しました。fixtureを有効な文字へ置き換えると提案の52チェックは成功しましたが、上記のケースはテストされていません。変更済みのfixtureも含め、保留部分は製品ソースへ取り込んでいません。

### F5：Discordの全体制限を失わないこと

Discordには送り先単位と全体の制限があり、429本文の`global`やヘッダーで区別します。提案は現在の結果型`.retry(seconds)`だけで待機範囲を狭めるため、全体制限を表現できません。採用するにはスコープと待機期限を保持し、ジョブの手動操作や削除でも必要な待機を失わない検証が必要です。[Discord公式](https://docs.discord.com/developers/topics/rate-limits)

Telegramにもチャット単位・Bot全体の制限があり、「すべてBot単位」と断定する説明は修正が必要です。Bot単位への待機共有自体は慎重側ですが、今回Discordと一体の変更をそのまま採用しません。[Telegram公式](https://core.telegram.org/bots/faq#my-bot-is-hitting-limits-how-do-i-avoid-this)
