# hi.newへの文字起こし送信（ネイティブiOS 0.10.1／38）

hi.newを送り先の1つとして選び、Discord／Telegramと併用できます。文字起こし本文だけを送信し、音声は添付しません。接頭語の設定も従来どおり「接頭語＋半角スペース＋本文」です。時刻・電圧の自動付加、アプリへの返信・会話表示、Muse側の定期監視は実装していません。Flutter版への展開も別段階です。

## 1. 送信側の準備

hi.newのWebサイトで、利用者自身がIndex Relay専用の送信者ハンドルを作成し、所有者メールの確認を済ませます。受信者のハンドルとトークンを送信側で使い回さないでください。アプリ内のハンドル取得、有料名の購入、setup codeの交換、復旧メール送信は今回の対象外です。

アプリには送信者のスコープ付きトークン（`hnt_…`）を推奨します。所有者トークン（`hn_…`）も使えますが、入力時に全権限を持つことを警告します。通常の送信には`profile:read`、`contacts:read`、`messages:send`が必要です。アプリで招待を使用する場合だけ`contacts:write`も必要です。トークンの発行・復旧はhi.new側で行います。チャットや公開Issueへトークン・招待リンクを貼らないでください。

## 2. 平文と保存設定

この版は`enc:"none"`で送ります。HTTPSで通信しますが、hi.newのサーバーへ平文が届きます。送信側・受信側それぞれの所有者画面で、transcript保持を無効化してください。受信側だけを無効にしても、送信者用のコピーが残り得ます。アプリはこの設定を自動確認・変更できないため、登録画面で利用者が確認します。

ACKは待機ペイロードを削除する操作で、所有者用のtranscriptとは別です。受信側は原文を永続保存し、メッセージIDで重複判定してからACKしてください。保存後の要約・通知処理は、失敗しても保存済み原文から再実行できるようにします。

## 3. アプリで接続する

1. 歯車 → 送り先・送信方法 → 送り先を追加 → サービス「hi.new」。
2. 送信者専用トークンと、受信者のハンドル（例：`reader-bot`、URLではない）を入力する。
3. 平文送信と、双方のtranscript保持設定を確認する。
4. まだ接続許可がなければ、信頼できる経路で受け取った招待を入力し、「招待を使用して接続…」から明示的に使用する。相互の送信許可が作られる。アプリは受信側へ返信しない。
5. 「送り先を確認して保存」。保存はプロフィール・grantの照合だけで、投稿しない。新しいhi.new送り先はオフで保存される。
6. 設定一覧で送り先をオンにする。最初は「送信前に確認する」もオンにする。
7. 必要なら「テスト文を確認待ちに追加」を押し、送信一覧で本文を確認して送る。自動送信設定でもテストは確認待ちになる。

登録・資格情報更新では送信者ハンドルと受信者ハンドルを照合します。別のアカウントや相手は新規送り先として登録します。招待redeemの応答を失った場合、既存のgrantを再照合して復旧します。同じ操作の中でredeemを繰り返しません。入力と異なる相手への招待だった場合、送信は有効化せず、hi.new側で接続状況を確認してください。

## 4. 通常の送信と受付表示

送り先がオンなら、今後保存する新しい文字起こしから対象になります。過去の文章は既存の「保存済みの文章を追加」から、確認待ちとして明示的に追加します。

APIの201はhi.newの受信箱への受付です。アプリの「hi.new受付済み」は、受信側の保存・要約・通知完了を意味しません。受付ID、未ACK本文の期限、冪等リプレイの有無を保存します。未ACK本文は7日で期限切れになります。アプリはACK状況をポーリングせず、受信者のトークンを必要としません。

## 5. 冪等性・失敗・復旧

送信キーは送り先ごとの永続`DeliveryJob.id`から`ir:<UUID>`として作り、試行ごとのUUIDとは分けます。同じ録音を複数送り先へ送っても衝突しません。hi.newのキーは送信者全体で共有されます。

送信開始後は本文と相手を固定します。同じ論理送信の再試行では同じキーを使用します。初回送信から24時間を超えると再送せず、送り先での確認を求めます。OSから復元する期限超過の転送にも取消を要求します。サーバー側の冪等記録は永久保存ではなく、監査行の清掃により失われ得るため、古いジョブを無期限に再送しません。

- 通信前に接続不能と確定した場合は再試行待ち。
- 送信タイムアウト、取消、5xx、不完全な成功応答は結果不明。自動再送せず、24時間以内だけ同じ本文・キーで明示的に再確認できる。
- 429は送信者ハンドル単位でクールダウンを共有。少なくとも1時間待ち、より長いRetry-Afterも尊重する。24時間を超える待機指定は送り先を停止して要対応にする。
- 401／402／403／404、鍵変更、暗号化要求、冪等キー衝突は送り先をオフにして要対応にする。先行する試行が結果不明なら、その不明状態も維持する。
- grant確認の一時的な通信障害は上限付きで再試行する。相手の`public_key`・`pinned_key`がnullでなくなった場合や`key_changed`は停止する。本文送信前にも照合し、サーバーにも`recipient_public_key:null`を渡す。
- 本文上限は接頭語込みでUTF-8の64,000バイト。既存2サービスの文字数上限・結果不明の再送ルールは変えない。

再確認しても24時間を過ぎた不明結果を解決できなければ、送り先で確認して「確認済み」または「再送せず終了」を選んでください。新しいキーを勝手に発行して再送する機能はありません。

## 6. セキュリティと既存データ

Bearerと招待は`https://hi.new`の限定したAPIだけへ送ります。リダイレクトは追いません。トークンは端末のKeychain、招待入力は画面内だけに保持し、接続確認後に消します。診断には送信本文・トークン・招待・APIの外部hintを出しません。公開前チェックも`hn_`／`hnt_`／`hns_`／`hni_`の実値らしい文字列を拒否します。

新しい保存項目はoptionalで、従来のDiscord／Telegram設定・ジョブを読み込めます。0.9.8以前は新しいhi.newプロバイダを解釈できないため、hi.newを登録した後の旧版への上書き復帰は互換性を保証しません。実機更新前に必要なデータを退避してください。

くろ側は`messages:read`で受信・ACKを行えます。headers／activityも使う場合は`messages:list`を追加します。`messages:send`を付けなければ、返信は構造的に制限できます。readという名称でもACKの削除権限を含む点に注意してください。

## 0.10.1のレビュー対応

- hi.newの実行枠がない場合と送信前照合中は、hi.newだけを選択対象から除外し、Discord／Telegramを進めます。照合中に他サービスが送信中になっても照合結果を捨てず、実行枠・対象ジョブ・送り先を再確認してhi.newの送信を登録します。hi.newの照合は同時に1件までです。
- 送信トークンはKeychainのほか、登録済みバックグラウンドURLSession要求にも含まれてOS側に保持されます。スコープ付きトークンで権限を絞ってください。
- 公開コードは通常送信・リプレイともHTTP 201です。互換対応としてHTTP 200でも`replayed:true`かつID・宛先・暗号方式・期限が妥当なら受付成功とします。単なる200や不完全な受付は結果不明です。`recipient_public_key:null`は鍵変更との競合時に平文を拒否させるため維持します。
- 429の待機時刻は結果不明でも表示し、待機中の再送操作には時刻付きの説明を出します。最低1時間の待機は維持します。
- 送信一覧で完了項目を表示し、送信済み・取消済みのテストを左へスワイプ、または詳細の「このテスト履歴を削除」で削除できます。確認待ちは先に「送信しない」にしてください。送信中・結果不明と通常の録音に対する受付履歴はこの操作では削除できません。送信者単位の待機を守るため、429待機中のテストも待機終了まで削除できません。
- Flutter版には今回の変更を取り込んでいません。展開時はRunnerのSwift登録、DartのhiNew表示、Androidの対応方針を別途実装・検証します。戻し用のネイティブ版はhi.new対応版（0.10.0以降）が必要です。

回帰テストは実行枠不足／照合中の共通選択ポリシーと永続ジョブの送信開始、再送応答、待機表示用エラー、削除制限をモックで確認します。ロック中のOS転送登録と実サービスの応答形は、実機での確認対象です。

0.10.1の検証：Swift全13スイート・660チェック（HiNew 141）、Python 49テスト、`inspect-bridge-network.py`、iPhone向けDebugビルドが成功しました。実サービスへの追加投稿は行っていません。
